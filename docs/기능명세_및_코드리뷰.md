# AITriggerForwarder — 기능 명세 및 코드 리뷰

> 작성일: 2026-05-21
> 대상 커밋: `a93a02d` (main)
> 검토 범위: `src/main/scala/.../Main.scala`, `application.conf`, `log4j2.xml`, `pom.xml`

---

## 1. 개요

AITriggerForwarder는 **AI inference server**가 보내는 HTTP POST 요청을 받아,
유효성 검증 및 설비 정보 보강(enrichment)을 거친 뒤 **EA server 내부 IF Service(EARS)** 로
시나리오 실행 요청을 전달하는 경량 포워딩 서버다.

- 언어/런타임: Scala 2.12.18 / JVM 8
- 프레임워크: Akka HTTP 10.1.15, Akka 2.6.20
- 데이터 저장소: MongoDB (설비 정보 `EQP_INFO` 조회 전용, 읽기만 수행)
- 로깅: Log4j2 (콘솔 + 롤링 파일)
- 배포 산출물: fat-jar (`mvn clean package`)

### 1.1 처리 흐름 요약

```
AI Server ──POST /ai_trigger──▶ AITriggerForwarder
                                     │
                                     │ 1. JSON 파싱
                                     │ 2. txn 생성
                                     │ 3. eqpid/scname 유효성 검증
                                     │
                                     ├──▶ MongoDB EQP_INFO 조회 (eqpId 기준)
                                     │
                                     └──▶ EARS /EARS/Action 호출 (POST, 5s 타임아웃)
                                     │
                                     ▼
                          200 {"status":"pass"}  또는  500
```

## 2. 기능 명세

### 2.1 수신 엔드포인트

| 항목 | 값 |
|------|----|
| 경로 | `POST /ai_trigger` |
| 바인딩 | `forwarder.interface`:`forwarder.port` (기본 `0.0.0.0:50050`) |
| 요청 Content-Type | `application/json` |
| 요청 본문 | `{ "eqpid": "<설비ID>", "scname": "<시나리오명>" }` |

요청 본문은 `AiTriggerRequest(eqpid: String, scname: String)` 케이스 클래스로 역직렬화된다
(`spray-json`, `jsonFormat2`).

### 2.2 유효성 검증

수신 직후 다음 검증을 수행한다.

1. `eqpid`, `scname` 각각에 대해 `null` 방어 후 `trim()` 적용.
2. 둘 중 **하나라도 빈 문자열**이면 요청을 거부하고 `500`을 반환(EARS 호출 생략).
3. 검증 통과 시 trim된 값으로 이후 처리(Mongo 조회·EARS 호출)를 진행한다.

> 참고: JSON 자체가 깨졌거나 필드가 누락된 경우는 이 검증에 도달하기 전에
> Akka HTTP의 기본 rejection 처리로 `400`이 반환된다(아래 4.2 항목 참조).

### 2.3 트랜잭션 ID (txn)

- `TxnGenerator.next()` = `System.currentTimeMillis().toString`.
- 요청 1건당 1개 생성되어 로그 추적 및 EARS `txn` 헤더로 전파된다.

### 2.4 설비 정보 조회 (MongoDB)

- 대상: `EARS` DB의 `EQP_INFO` 컬렉션.
- 쿼리: `eqpId == <trim된 eqpid>`, 첫 번째 문서 1건 조회.
- 필드 매핑:

  | Mongo 필드 | `EqpInfo` 필드 | 용도 |
  |-----------|---------------|------|
  | `eqpId`   | `id`          | 로그 |
  | `process` | `process`     | EARS `process` 헤더 |
  | `eqpModel`| `model`       | EARS `model` 헤더 |
  | `lineDesc`| `lineDesc`    | EARS `line` 헤더 |
  | `ipAddr`  | `ip` (Option) | 로그 (공백 제거·빈 값 제외) |

- 조회 결과:
  - **문서 있음** → EARS 호출로 진행.
  - **문서 없음** → `500` 반환.
  - **조회 예외** → `500` 반환 (`MongoEqpInfoRepository.find` 내부에서 예외를 잡아 `None`으로 변환하므로, 실제로는 "문서 없음" 경로와 동일하게 처리됨).

### 2.5 EARS(IF Service) 전달

`EarsClient.callEars`가 다음 요청을 생성해 `forwarder.ears.url`로 POST 한다.

**HTTP 헤더**

| 헤더 | 값 | 출처 |
|------|----|----|
| `category`  | `recovery` (고정) | 하드코딩 |
| `process`   | EQP_INFO.process | Mongo |
| `model`     | EQP_INFO.eqpModel | Mongo |
| `line`      | EQP_INFO.lineDesc | Mongo |
| `eqpid`     | 요청 eqpid (trim) | 요청 |
| `name`      | 요청 scname (trim) | 요청 |
| `txn`       | 트랜잭션 ID | 생성값 |
| `triggerBy` | `AI` (고정) | 하드코딩 |

**HTTP 본문 (`application/json`)**

```json
{
  "@Trigger": "AI",
  "@UserInfo": "AI Server",
  "@StartStep": "1",
  "UserText": "Scenario=<scname>, Eqpid=<eqpid>"
}
```

**타임아웃**: `forwarder.ears.timeout`(기본 5s). `Future.firstCompletedOf`로
실제 응답 Future와 타임아웃 Future를 경쟁시켜, 먼저 끝나는 쪽을 채택한다.

### 2.6 응답 규약

| 상황 | HTTP 상태 | 본문 |
|------|-----------|------|
| EARS 2xx 응답 | `200 OK` | `{"status":"<forwarder.response-pass-status>"}` (기본 `"pass"`) |
| 유효성 검증 실패 | `500` | (없음) |
| EQP_INFO 미발견 | `500` | (없음) |
| Mongo 조회 실패 | `500` | (없음) |
| EARS 비-2xx 응답 | `500` | (없음) |
| EARS 호출 실패/타임아웃 | `500` | (없음) |
| 라우트 내 미처리 예외 | `500` | (없음) |

### 2.7 설정 항목 (`application.conf`)

| 키 | 기본값 | 설명 |
|----|--------|------|
| `forwarder.interface` | `0.0.0.0` | 바인딩 인터페이스 |
| `forwarder.port` | `50050` | 수신 포트 |

### 2.8 로깅

- `log4j2.xml`: 콘솔 + 롤링 파일(`logs/forwarder.log`, 일 단위·20MB 롤오버, 14개 보관).
- 주요 로그 지점: 요청 수신, 검증 실패, EQP_INFO 조회 결과, EARS 호출 완료(상태·소요시간), 각종 실패.
- 모든 로그 라인에 `txn`이 포함되어 단일 요청 추적이 가능하다.

### 2.9 생명주기

- 기동: `Main`에서 `ActorSystem` 생성 → 설정 로드 → Mongo repo / EARS client / 라우트 구성 → 포트 바인딩.
- 바인딩 실패 시 로그 후 `system.terminate()`.
- 종료: shutdown hook이 Mongo 클라이언트 close 및 `ActorSystem` 종료 수행.

## 3. 코드 리뷰

### 3.1 잘 되어 있는 점

- **계층 분리**: `EqpInfoRepository`(trait) / `EarsClient` / `ForwarderRoutes`로 책임이 분리되어 있고, repo가 trait로 추상화되어 테스트·교체가 용이하다.
- **txn 기반 추적성**: 모든 로그에 `txn`이 일관되게 포함된다.
- **방어적 입력 처리**: `Option(req.eqpid).getOrElse("").trim`으로 null·공백을 함께 방어한다.
- **응답 엔티티 소비**: EARS 응답에 대해 `discardEntityBytes()`를 호출해 (정상 경로 한정) 커넥션 누수를 방지한다.
- **자원 정리**: shutdown hook에서 Mongo 클라이언트를 닫는다.

### 3.2 개선 권고 — 우선순위 높음

#### R1. HTTP 상태 코드 오용 — 모든 실패가 `500`

유효성 검증 실패, EQP_INFO 미발견, EARS 비-2xx 응답이 모두 `500 InternalServerError`로 반환된다.
- 검증 실패는 **클라이언트 오류**이므로 `400 Bad Request`가 적절하다.
- EQP_INFO 미발견은 `404`/`422` 등으로 구분하는 편이 적절하다.
- 현재 규약으로는 AI Server가 "내가 잘못 보냈는지" vs "서버/하위 시스템 장애인지"를 구분할 수 없어,
  재시도 정책 수립이 불가능하다.
- 위치: `ForwarderRoutes.route` 전반 (`Main.scala:197, 210, 213, 217, 220`).

#### R2. txn 충돌 가능성

`txn = System.currentTimeMillis()`는 **동일 밀리초 내 동시 요청** 시 같은 값이 생성된다.
로그 상관관계가 깨지고, EARS 측에서 txn을 키로 사용할 경우 충돌이 발생한다.
- 권고: `UUID`, 또는 `밀리초 + AtomicLong 카운터`, 또는 `nanoTime` 기반으로 유일성을 보장.
- 위치: `TxnGenerator.next()` (`Main.scala:168-170`).

#### R3. Mongo 자격 증명 평문 커밋

`application.conf`에 `password = "ars2015!"`가 평문으로 들어 있고 Git에 추적되고 있다.
- 권고: 환경변수/시스템 프로퍼티/시크릿 매니저로 외부화하고, 가능하면 Git 이력에서 제거.
- 위치: `application.conf:19`.

#### R4. EARS 타임아웃 시 커넥션 누수

`Future.firstCompletedOf(List(responseF, timeoutF))`에서 **타임아웃이 이기면**, 실제
`http.singleRequest`의 응답 Future는 그대로 방치된다. 이후 응답이 도착해도 그 엔티티가
소비/폐기되지 않아 Akka HTTP 커넥션 풀이 점진적으로 고갈될 수 있다.
- 권고: `responseF`에 콜백을 걸어 늦게 도착한 응답도 `discardEntityBytes()` 처리하거나,
  Akka HTTP 자체의 요청 타임아웃 설정을 사용.
- 위치: `EarsClient.callEars` (`Main.scala:154-164`).

### 3.3 개선 권고 — 우선순위 중간

#### R5. Mongo 문서 매핑 오류가 "미발견"으로 은폐됨

`MongoEqpInfoRepository.find`에서 `doc.getString("process")` 등은 필드가 없거나 문자열이
아닐 경우 예외를 던진다. 이 예외는 `.recover`에 잡혀 `None`이 되고, 라우트에서는
"EQP_INFO 미발견"과 동일하게 처리된다. 즉 **데이터 정합성 오류가 조회 실패로 위장**된다.
- 권고: `Option(doc.getString(...))` 패턴을 모든 필드에 적용하거나, 매핑 실패와
  문서 부재를 구분해 로깅·반환.
- 위치: `Main.scala:104-118`.

#### R6. JSON 파싱 실패 경로의 응답 규약 불일치

본문 JSON이 깨졌거나 필드가 누락되면 Akka HTTP 기본 rejection 처리로 `400`이 반환되는데,
빈 문자열 검증 실패는 `500`을 반환한다. **같은 "잘못된 요청"이 경로에 따라 400/500으로 갈린다.**
- 권고: 명시적 `RejectionHandler`를 등록해 파싱 실패 응답 형식을 통제하고,
  검증 실패 응답과 규약을 통일(R1과 함께 정리).
- 위치: `ForwarderRoutes` — rejection handler 부재.

#### R7. 실패 응답에 본문 부재 — 비대칭 규약

성공은 `{"status":"pass"}` JSON을 반환하지만 모든 실패는 본문 없이 상태 코드만 반환한다.
AI Server가 응답 본문을 일관되게 파싱한다면 실패 시 파싱 오류가 발생할 수 있다.
- 권고: 실패에도 `{"status":"<fail값>", "reason":"..."}` 형태의 일관된 JSON 본문 제공
  (실패 status도 설정값으로 외부화 검토).

#### R8. README / 문서 최신화 필요

- `README.md`가 `StubEqpInfoRepository`("Mongo 조회는 스텁") 기준으로 작성되어 있으나,
  실제 코드는 `MongoEqpInfoRepository`로 구현 완료된 상태다.
- README의 산출물 jar 이름 `AITriggerForwarder-0.1.0-SNAPSHOT-jar-with-dependencies.jar`는
  실제(`artifactId=aitriggerforwarder`, `version=1.0-SNAPSHOT`, `appendAssemblyId=false`)와
  불일치한다. 실제 산출물명은 `aitriggerforwarder-1.0-SNAPSHOT.jar`.
- README의 log4j 버전 언급(2.17.2)과 `pom.xml`(2.17.1)이 불일치.

#### R9. 빌드 플러그인 중복

`pom.xml`에 `maven-assembly-plugin`과 `maven-shade-plugin`이 **모두** `package` 단계에서
fat-jar를 생성한다. 두 산출물이 같은 좌표를 두고 경쟁/덮어쓰기 하므로 빌드 결과가
혼동된다. 하나(권장: shade)로 통일할 것.
- 위치: `pom.xml:127-222`.

### 3.4 개선 권고 — 우선순위 낮음 / 관찰 사항

- **R10. Deprecated API**: `ActorMaterializer`, `Http().bindAndHandle`는 Akka 2.6에서
  deprecated다. 동작에는 문제없으나 `Materializer`는 system에서 자동 도출되며
  `Http().newServerAt(...).bind(...)` 사용이 권장된다.
- **R11. 헬스체크 엔드포인트 부재**: `/ai_trigger` 외 라우트가 없어 LB·모니터링용
  health check가 불가능하다. `GET /health` 추가 검토.
- **R12. 매직 값**: `category=recovery`, `@StartStep=1`, `@Trigger=AI` 등이 하드코딩되어
  있다. EARS 규약이 고정이면 상수로 명시, 가변 가능성이 있으면 설정화 검토.
- **R13. 테스트 부재**: `pom.xml`은 `src/test/scala`를 지정하나 테스트 코드가 없다.
  repo가 trait로 추상화되어 있어 라우트 단위 테스트(`akka-http-testkit`) 도입이 용이하다.
- **R14. Mongo 기동 시 연결 검증 없음**: `MongoClient`는 지연 연결이므로 기동 시
  Mongo 장애가 드러나지 않고, 매 요청에서 실패한다. 기동 시 ping 검증 검토.
- **R15. `extractClientIP`**: `Remote-Address` 헤더가 없으면 `unknown`이 로깅될 수 있다.
  필요 시 `akka.http.server.remote-address-header = on` 설정.

## 4. 부록

### 4.1 빌드 / 실행

```bash
# 빌드
mvn -U clean package -DskipTests
# 산출물: target/aitriggerforwarder-1.0-SNAPSHOT.jar

# 실행
java -jar target/aitriggerforwarder-1.0-SNAPSHOT.jar

# Windows (PowerShell 인자 파싱 회피)
java "-Dconfig.file=application.conf" "-Dlog4j.configurationFile=log4j2.xml" -jar aitriggerforwarder-1.0-SNAPSHOT.jar
```

### 4.2 네트워크 요구사항

- AI Server → Forwarder: inbound TCP `50050`.
- Forwarder → MongoDB: outbound TCP `12.93.14.33:50042`.
- Forwarder → EARS: outbound TCP `12.93.14.33:50007`.

### 4.3 동작 확인 (curl)

```bash
# 정상 케이스 → 200 {"status":"pass"}
curl -X POST http://localhost:50050/ai_trigger \
  -H "Content-Type: application/json" \
  -d '{"eqpid":"1AFDE04_DU01","scname":"BC_FLOW_RECOVERY"}'

# 빈 값 → 500 (EARS 호출 생략)
curl -X POST http://localhost:50050/ai_trigger \
  -H "Content-Type: application/json" \
  -d '{"eqpid":"","scname":""}'
```
